# CONTRIBUTING / Правила за принос

Този документ описва начина на работа по документацията на учебното приложение Notes API в Упражнение 2. Всеки Issue се изпълнява в отделен Git клон и се интегрира в `main` чрез Pull Request (PR). Програмният код на приложението не се променя по време на упражнението.

## Именуване на клони

- Основният клон е `main`; не правим директни промени в него.
- За всяка задача използваме отделен клон по схемата `docs/tNN-short-description`, където `NN` е номерът на задачата от `BACKLOG.bg.md`.
- Имената се пишат с малки латински букви и тирета между думите.
- Примери: `docs/t03-service-description`, `docs/t06-contributing-guidelines`, `docs/t07-glossary-a`.

Пример за създаване и публикуване на нов клон от актуалния `main`:

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c docs/t06-contributing-guidelines
git push -u origin docs/t06-contributing-guidelines
```

## Правила за commit съобщения

- Всеки commit трябва да представлява една логически завършена промяна.
- Използваме кратко и описателно съобщение с префикс: `docs:`, `fix:` или `chore:`.
- Не използваме неясни съобщения като `update`, `test` или `changes`.
- Примери:
  - `docs: describe Notes API endpoints (T03)`
  - `docs: add contributor guidelines (T06)`
  - `fix: correct a broken documentation link (T09)`

Преди commit преглеждаме промените:

```bash
git status
git diff
git add CONTRIBUTING.md
git commit -m "docs: add contributor guidelines (T06)"
```

## Правила за Pull Requests

1. Всяка задача от `BACKLOG.bg.md` има отделен Issue, клон и PR към `main`.
2. Заглавието на PR съдържа номера на задачата и кратко описание, например `T06: Add contributing guidelines`.
3. В описанието на PR се посочват направените промени, начинът на проверка и свързаният Issue с `Closes #4` за T06.
4. Преглеждаме раздела **Files changed** за случайни изменения или оставени маркери за недовършена работа.
5. Ако има конфликти, разрешаваме ги преди сливането. В задачите, които го изискват, използваме `git fetch`, `git merge origin/main` или `git rebase origin/main` според `BACKLOG.bg.md`.
6. Използваме **Merge pull request** след необходимите проверки; не правим директен `git push` към защитения `main`.
7. След успешно сливане проверяваме дали свързаният Issue е затворен и актуализираме състоянието в GitHub Project.

### Преглед и индивидуално изпълнение

При работа в екип партньорът прави ревю на PR и при необходимост предлага корекция чрез **Suggest changes**. За това упражнение преподавателят е разрешил индивидуално изпълнение от `@Tedi077`. Затова PR се преглеждат самостоятелно, без да се представя самооценката за чуждо одобрение. Задължителното одобрение от втори човек и задължителното Code Owner review не се включват, тъй като авторът не може да одобри собствения си PR.

## Проверки преди сливане

- Променяме само файловете, които са свързани с текущата задача.
- Сверяваме техническите описания с реалните файлове на приложението.
- При изменения само по документацията проверяваме Markdown съдържанието и линковете.
- При приложими проверки използваме `pytest` и `ruff check .` според `README.md`; не твърдим, че тестове са изпълнени, ако не са стартирани.

Branching strategy: GitHub Flow — използваме краткотрайни клони за отделните задачи и Pull Requests към main, защото учебният проект има един основен клон и не изисква отделни develop и release клони.
